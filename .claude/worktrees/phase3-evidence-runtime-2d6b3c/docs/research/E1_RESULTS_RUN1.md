## Interpretation and caveats (written by the architect, not generated)
1. **B1 is far better than random but far from solved.** Test PR-AUC about 0.49 against a base rate of about 0.0011, ROC-AUC about 0.98. At 100 alerts the precision is about 0.97, but recall at 1,000 alerts is only about 0.47 and about 0.73 at 5,000: roughly half of laundering transactions are ranked low.
2. **B0 as specified is not a meaningful baseline.** Its PR-AUC (0.00122) is about the base rate. Two rules never fire because their thresholds (24h fan-out >= 25,709; 1h velocity >= 1,207) are the 99.9th percentile over transactions, which a few very high-volume accounts dominate. The rule pack was not tuned (by design); a v2 with per-account thresholds, tuned on validation only, should be reported alongside v1, never instead of it. Recall@k for B0 is 0 partly because most rows tie at zero rules fired (ties broken by row order).
3. **Where the signal comes from.** Features-only-intrinsic reaches test PR-AUC 0.054 (ROC 0.92); adding account and pair history raises it to about 0.49. `fmt` (payment format) has the largest gain. This is a statement about this synthetic generator; it may reflect generator artefacts (for example laundering accounts with distinctive history) and should not be read as evidence about real laundering. Not investigated yet.
4. **Leakage checks done:** features are point-in-time (property test: later events never change earlier rows); labels are fetched by a separate module the feature code cannot import; thresholds came from unlabeled train features; split is chronological. **Not done:** an explicit check that history features (which include earlier test-window transactions, unlabeled) are legitimate under an as_of reading, and a shuffled-label sanity run.
5. **Short-horizon shift (RQ5, D-24):** every seed scores lower on test than on validation (-0.029, -0.035, -0.042 PR-AUC), but validation was used for early stopping and seed selection (optimistic bias), seed spread is about 0.01, and windows are two days with about 1,000 positives each. No window-to-window noise estimate exists, so this is **not** evidence of degradation yet.
6. **Calibration:** the isotonic calibrator fitted on validation is well calibrated on test (ECE 0.0003) but badly off on the stress slice (ECE 0.24; mean calibrated 0.35 vs actual 0.59), because the stress regime has a very different positive rate (59% vs 0.1%). Raw XGBoost outputs are not probabilities (the 0.03 raw ECE is shown only to illustrate that). A calibrated probability is valid only under the prevalence it was fit on.
7. **Stress slice** numbers are on 1,108 rows, 59% positive; PR-AUC there is not comparable with test, and intrinsic-only beating the full model there (0.970 vs 0.945) is unexplained.
8. **Timing (this workstation, 20 logical cores, 16 GB):** loading 5.08M rows 59 s; building features 15 s; whole run 257 s including 4 model fits. These are measurements for the batch path, not per-case latency (NFR-PERF-02 is not yet measured).
