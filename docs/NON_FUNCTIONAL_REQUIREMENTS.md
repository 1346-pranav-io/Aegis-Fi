# Non-Functional Requirements

Status: DRAFT · Version 0.1.
**Important:** numeric values below are **design targets chosen by the architect, not measurements.** They must be validated or revised against real benchmarks in Phase 2–6, and any change recorded in `decisions.md`.

## NFR-PERF — Performance (targets)
| ID | Target | Rationale | Verification |
|---|---|---|---|
| NFR-PERF-01 | Batch ingestion: design target ≥ 50k records/s per worker on a developer workstation (bulk `COPY`) | Benchmark datasets are large | Benchmark in Phase 1; report actual |
| NFR-PERF-02 | Deterministic analysis steps for one case (Transaction/Graph/Behaviour) complete within 30 s at p95 on benchmark-scale data | Interactive triage | Benchmark |
| NFR-PERF-03 | End-to-end investigation within configured budget (default 10 min wall, bounded LLM tokens); never unbounded | Cost/predictability | Budget tests |
| NFR-PERF-04 | API read endpoints p95 < 500 ms excluding long-running runs | UI responsiveness | Load test |
| NFR-PERF-05 | Graph module declares its supported graph size and fails with a clear error above it | Avoid OOM (R-05) | Test |

## NFR-SCAL — Scalability
- NFR-SCAL-01 Workers scale horizontally via the Postgres job queue (D-03); no in-process global state.
- NFR-SCAL-02 Stateless API; all run state in Postgres.
- NFR-SCAL-03 Graph analytics operate on windowed subgraphs per case, not whole-dataset graphs, in the investigation path.

## NFR-REL — Reliability and error handling
- NFR-REL-01 Every external call (LLM, DB) has timeout, bounded retries with backoff, and a typed failure result.
- NFR-REL-02 Agent failure degrades the investigation (marked `PARTIAL`, failed step recorded) rather than aborting silently or fabricating output.
- NFR-REL-03 Runs are resumable from checkpoints (FR-ORC-05).
- NFR-REL-04 LLM output that fails schema validation is retried at most N times, then recorded as a failed step.
- NFR-REL-05 Jobs are idempotent; duplicate delivery must not create duplicate evidence (idempotency keys).

## NFR-SEC — Security
- NFR-SEC-01 AuthN via OIDC-ready bearer tokens; RBAC roles per D-15; deny by default.
- NFR-SEC-02 Secrets only via environment/secret store; never in repo, logs, prompts or evidence.
- NFR-SEC-03 App DB role has least privilege; source schema insert/select only (D-04); separate migration role.
- NFR-SEC-04 PII minimisation: pseudonymise before any LLM call (D-10); logs avoid raw identifiers.
- NFR-SEC-05 Prompt-injection resistance: text from documents/transactions is treated as data; LLM outputs cannot trigger tools outside the allow-list; tool arguments validated against schemas; no LLM-originated SQL.
- NFR-SEC-06 Dependency scanning and lockfile pinning in CI.
- NFR-SEC-07 Audit log is append-only and covers all approvals and data access.
- NFR-SEC-08 Encryption in transit for all network paths; at-rest encryption via DB/volume configuration documented for any non-dev environment.
- NFR-SEC-09 Security review (security-reviewer agent + human) required before each phase exit.

## NFR-AUD — Auditability and explainability
- NFR-AUD-01 Every conclusion reconstructable to source records (SAC-01).
- NFR-AUD-02 Every LLM call logged with model id, prompt version, input hash, output (post-pseudonymisation).
- NFR-AUD-03 Every model artefact versioned with training manifest hash, code commit, metrics.
- NFR-AUD-04 Rule sets versioned.

## NFR-REP — Reproducibility
- NFR-REP-01 Dependencies locked; Docker image digest recorded in each run.
- NFR-REP-02 Seeds recorded; deterministic code paths are bit-reproducible on same platform.
- NFR-REP-03 LLM nondeterminism handled by record/replay for experiments; live-LLM runs reported with repeat counts and variance.
- NFR-REP-04 Dataset manifests with content hashes; no unversioned data in experiments.
- NFR-REP-05 Temporal splits generated by code from config, not by hand.

## NFR-MNT — Maintainability and quality
- NFR-MNT-01 Typed code: mypy strict passes on core packages.
- NFR-MNT-02 Layered module dependencies enforced by an import-linter check in CI.
- NFR-MNT-03 Unit-test coverage target ≥ 85% on core logic (domain, evidence, verification, orchestration); coverage is a floor, not a goal.
- NFR-MNT-04 No duplicated capability: new modules must be justified against the component map in SYSTEM_ARCHITECTURE.md.
- NFR-MNT-05 Documentation updated with the change that requires it.

## NFR-PRIV — Privacy and data governance
- NFR-PRIV-01 Research repo contains only public/synthetic data (D-11).
- NFR-PRIV-02 Retention and deletion policy defined before any non-synthetic data is handled (blocked on Q-01).
- NFR-PRIV-03 Data minimisation in prompts and exports.

## NFR-USE — Usability
- NFR-USE-01 UI always distinguishes verified / unverified / unsupported claims.
- NFR-USE-02 UI shows scores labelled "score" (and "calibrated probability" only when calibration exists).
- NFR-USE-03 Self-reported LLM confidence is visually separated and labelled as such.

## NFR-COST — Cost control
- NFR-COST-01 Per-run and per-experiment LLM budget caps enforced in the gateway.
- NFR-COST-02 Cost recorded per agent step and aggregated per case.

## NFR-PORT — Portability
- NFR-PORT-01 Runs on Linux/macOS/Windows via Docker Compose; no cloud-vendor lock-in.
- NFR-PORT-02 LLM provider isolated behind gateway interface so a local-model fallback could be added without agent changes.

## Acceptance of NFRs
An NFR is accepted when its verification exists in CI (automated) or is recorded in a phase-exit review (manual), and the result is stored. Unmeasured targets remain labelled "target".
